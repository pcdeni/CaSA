The experiment trail

What we tried, how it went (and why), and what each result pointed to next.

How to read this. Every entry has the same four parts: Tried (the idea), Result (what the silicon said), Why (the mechanism behind the outcome), and Pointed to (what it changed about the plan). The honest verdicts are the point — the wall-neutral and negative results built the cost model that now drives everything, and several of the biggest wins started life as failures.

win wall-neutral negative reversed later discovery lesson

Hardware shorthand: the rig drives four DDR4 modules through one FPGA (BCU1525). Benders 0 and 2 are two different SK hynix modules (bender 2 is the dual-rank production die); benders 1 and 3 are two different Micron modules. A "tuple" is a calibrated 16-row set that computes MAJ3; a "doubleACT" is the timing-violating double activation that makes rows share charge.

The XOR-8 "corruption" discovery

Tried Ordinary calibrated doubleACT operations.
Result Every operation also wrote the source row's bits into the row at address src XOR 8. It looked like data corruption.
Why Rows whose addresses differ in specific bits co-activate — the row decoder fires several wordlines under the violated timing.
Pointed to First a workaround (stride-16 pool layouts). Months later, the entire lattice program: the bug became the instrument.

The readout floor negative

Tried A CaSA-shaped compute pipeline, benchmarked against a CPU.
Result Disqualified: reading the amplified outputs cost ~8× the useful data.
Why The shape produces more readout bytes than compute value; the host pays for every byte.
Pointed to "Readout is the enemy" became design law, and MVDRAM (arXiv 2503.23817) became the peer system to reproduce and compare against.

The "probabilistic XDMA stall" lesson

Tried Living with weeks of intermittent DMA stalls blamed on the driver.
Result Root cause: program finalization ran on every execution, silently corrupting any program object executed more than once. One flag fixed it; 100-iteration re-execution now runs clean.
Why The finalizer re-inserted bookkeeping packets and OR-ed branch targets over baked bits — growth and garbage on re-run.
Pointed to Upstream DRAM-Bender carries the same latent bug (outreach item). Also: "probabilistic" is usually a deterministic bug seen from too far away.

Request-path profiling hypothesis killed

Tried Instrumenting the server, suspecting the Python client's request assembly was half the wall.
Result Wrong: the client keeps the pipe full (~0.2 ms gaps). The handler is ~3 ms ≈ one program round-trip, and receive time is dominated by a fixed ~1.5 ms DMA wake, nearly independent of size.
Pointed to The real currency: host↔DRAM round-trips. Batching and packing became the levers — and they delivered the only real wall moves of the week (−12.7% stacked).

SEG_POP readback (bitstream build-7) wall-neutral

Tried Cut readback bytes 4× by returning per-segment popcounts instead of raw rows.
Result Silicon-exact, production token-identical — and the wall didn't move.
Why Receive time is latency-bound, not byte-bound; fewer bytes per wake changes nothing.
Pointed to Byte savings are banked, to be cashed once round-trips amortize. First confirmation of the cost model.

Bank scale-out win wall-neutral

M3 coset-deposit scratch loading — gates 1 & 2, then the whole lever harness win production-dead

Tried Replace the per-column weight write (≈4,500 instructions, 3 programs) with one lattice deposit from a resident row.
Result In a standalone harness it looked spectacular: byte-exact on production pools, both dies, at 17 instructions in 1 program — 265.8× fewer instructions, ~4× wall; deposits chain (a deposit target is a valid clone source), fan-out to 7 rows per operation is clean, and 32 loads packed into one program ran 114× faster than the write path. Then production adoption was measured, and it resolved negative (07-26): the MAJ3 body recomputes its scratch row from the pool, so the deposited shadow is never read — suppressing every deposit (PIM_BCAST_NODEP=1 A/B) leaves the token identical. 99.4% of the "deposits" were d=0 no-ops; the only live effect is write elision, and 87% of that serves stale masks; the ceiling is <9% of the wall regardless.
Why The 265×/114× ratios are real in isolation, but the lever attacks only the ~8.6% column-write slice and its mechanism was never wired to the row that actually gets read. Both facts had to be measured to kill it — an impressive internal number is not a wall win, and a passing token gate is not a numerics proof (the layer-0 gate answered "Paris" with 87% of masks stale).
Pointed to Publicly retracted (PR #16, merged 07-28; trailing pointer annotation in PR #18), server machinery excised (−286 lines). The lattice deposit primitive stays bit-exact and real — only the production lever is dead. And the numerics-gate discipline this forced (per-op correlation, never token identity) became the instrument that later killed X-master too (Act VIII).

Act VI July 23 · what the noise turned out to be

The streaming "corruption" that wasn't discovery methodology

Tried The producer loop's first full-model run diverged. A per-op dump showed the streamed answer differing from the legacy one on a specific, structured set of elements — only the odd-indexed ones, every operation, phase-locked. It looked exactly like a digital bug in the readout packer.
Result A day of chasing plausible mechanisms — byte lanes, packing counters, fetch hazards — each refuted. Then the cheap control nobody had run: compare two legacy runs to each other. They differed identically — same odd-only structure, same magnitude. The effect had nothing to do with streaming. Any two separate server processes disagree on ~all odd 32-bit segments (the upper half of every 64-bit transfer — chips 4–7 of the module), plus the same fixed 13 even ones, deterministically within a boot.
Why Unmodeled structural determinism masquerades as noise. The comparison itself was invalid: cross-process results were never comparable, because a per-boot analog operating point (the chip's init/training state) sets a slightly different margin for the upper DQ half. We had been reading a boot-to-boot silicon fingerprint and calling it a datapath fault.
Pointed to A new instrument and a new rule. The instrument: a captured production request stream replayed twice inside one process, legacy-vs-streamed back-to-back — the only comparison below the cross-process floor. The rule, now standing: gate ≈ control, and design the control first. It converted a phantom bug into a determinism map (screened kernels bit-exact; resident matmuls bit-exact but for refresh-straddle steps; raw un-screened requests ~95%-element metastable jitter that the vote/margin stack silently absorbs; the per-boot shift on top).

codes: the inversion · PIM_REQ_CAPTURE + replay --dup · memory cross_process_floor · PR #12

The producer loop, exonerated and measured wall-neutral alone discovery

Tried With streaming exonerated, the same-process gate could actually bless it: replay twins, gate ≈ control to within one element in 345 requests.
Result Streaming on is token-identical and cuts per-program fetch — but at the request level it is wall-neutral (−4.0%, reverted default-off, not shipped). The receive is synchronous and dominates (~64% of the wall), so streaming the send cannot overlap it. The real attack on recv is phase-2 — issue program N+1's send past N's receive on independent PCIe channels — first projected here in Verilator, but blocked on RTL that would not reach fabric until build-14 (Act VII) and only validated on silicon later (Act VIII, −26.3%).
Why Streaming alone does not invert the regime, as first believed: recv is synchronous, so overlapping the send buys nothing. Program count is not the wall either (a K-batching lever, tried honestly, came back +19.3%). The one term left to attack is the un-overlapped receive latency — which only phase-2 pipelining touches.
Pointed to The controller-native execution regime MVDRAM describes — the command bus as the clock — but first the streaming fetch path had to actually work on silicon, which turned into the fetch saga (Act VII).

codes: Rung 1 → phase-2 · PIM_STREAM / PIM_STREAM_PIPE · memory rung1_streaming_validated · PR #14

Act VII July 24 · the fetch saga

A one-in-4,000 stall that was deterministic all along discovery simulation

Tried The pipeline ran clean for thousands of requests, then wedged. It smelled like a rare race — but "rare stochastic" and "deterministic with a deferred trigger" look identical in one sample.
Result A rerun sailed past the first stall point: position not fixed, so environmental arrival, not a fixed counter. The simulation testbench — extended with randomized program lengths and execution times instead of the fixed values it had always used — reproduced the loss instantly, 3 of 3 seeds, and self-shrank it to a four-program script. The fetch stage re-loops pc=0…END between a program's end and its completion signal; any hold parks the counter at an arbitrary phase, and the next program resumes from it, losing its first words. Latent in the legacy path too — masked for the project's whole life because every testbench pinned the timing that happened to land the freeze on zero.
Why Every parameter a testbench fixes is an assumption in disguise, and this bug lived exactly in the pinned dimension. The happy path was verified faithfully; the failure was never aimed at.
Pointed to Randomized stress with a checker as a permanent pre-flash gate. The fix (build-11): a program-start strobe forcing the counter to zero. Regression across every scenario plus 5×4,000 randomized programs: clean.

codes: build-11 / magic 0A · scenario F (self-shrinking) · fetch_restart · PR #14

The fix that broke the thing the sim couldn't see the model's edge

Tried Flash build-11. The streaming ladder passed clean — the stall was cured on silicon.
Result But one arm regressed: streamed branch-loop writes — the exact shape production's fused bodies use — now corrupted, where they had been fine before. The restart strobe un-parks the previous program's re-loop from where a branch used to harmlessly strand it, and that stale state becomes execute-visible. A branch-capable testbench (branches had been tied off) exercised the shape — but still couldn't reproduce the exact failure, because it happens where fetch crosses into the decode/execute side the sim stubs.
Why An ALL_PASS from a simulation is a statement about the verification boundary, not the design. This fix changed an invariant whose consumers live across that boundary; the moment a fix does that, the sim goes structurally silent on it. It is the same edge the end-to-end memory model has: the model omits exactly the part you're overlooking.
Pointed to Build-12: rather than patch symptoms, remove the disease — fetch parks at end-of-program until a restart strobe, so the whole stale-state hazard class (stale counter, stale branch, post-end junk) cannot exist. A clean idea that flashed correctly — and was NO-GO on silicon, in a way that finally exposed the bug under the whole arc (next card).

codes: build-12 / magic 0B · park-at-END (WAIT_RESTART) + branch fence · scenario I · PR #14

The three-line wiring bug under the whole silicon arc discovery simulation

Tried Flash build-12's park-at-END. Instead of curing the stall it wedged: every program after the first jammed the h2c channel (errno-512).
Result A new end-to-end pipeline sim — real decode/execute/regfile/maintenance on the real microcode — reproduced the wedge cycle-exact. Parking fetch at END left the conveyor stuck when the next maintenance event (tPRDI ≈ 1 µs, between every round-trip) arrived, because maintenance flows through fetch, not around it. Chasing that surfaced the real culprit under builds 11, 12 and 13: the QUAD wrapper softmc_core.v never connected fetch_restart/restart — a Synth 8-7071 the toolchain had flagged and nobody read — so the silicon ran restart==0 and none of the three RTL fixes had ever reached the fabric.
Why Every build since 11 had "fixed" the loss window in RTL that was disconnected in the wrapper; the sim always exercised the connected module, so it stayed green while silicon stayed broken. The end-to-end instrument — the one carrying maintenance and the real microcode — is what finally crossed the boundary the keyhole testbenches stubbed.
Pointed to Build-14: a 3-line wiring fix put the loss-window fix on silicon at last (ladder ALL_PASS, legacy twin gate exact, wedges now self-heal via process restart). That unblocked the streaming fetch path production had been waiting on — and with it, the phase-2 pipeline could finally be validated on real silicon (Act VIII). Current silicon is build-26 (magic 0x15).

Act VIII July 27 – 28 · the second campaign

Coarser activation quant across three families win

Tried Send fewer activation bitplanes per matvec — the top K instead of all 8 (PIM_ACT_K) — which is fewer round-trips per projection. Client-side only, no bitstream.
Result Token-identical and correlation-gated (per-op corr, never token identity — the M3 lesson): K=6 for both Bonsai variants (1-bit −21.7%, ternary −22.2% full-model wall) and K=5 for BitNet-2B (−32.2%). K=4 collapses everywhere — a genuine quant cliff — so the floor tracks the training recipe, not the weight bits; the defaults differ per family and all three shipped 07-28.
Pointed to A wall lever that costs nothing on the card and generalizes across the whole model zoo — the first half of the current production stack.

Phase-2 send-ahead on silicon — the −64.7% stack win

Tried With build-14 finally putting the fetch path right on fabric, run the phase-2 pipeline (send program N+1 past N's receive on independent PCIe channels) as a real silicon A/B on the live build-26.
Result −26.3% full-model wall (2529.1 → 1863.1 s), and the number that matters: per-request recv 112 → 57 ms (halved) — the first production lever to cut the receive latency Act IV named as the 65% wall. 0 stalls, 0 decay, 0 errors over 11,500 requests (the projected ~1/4k stall never appeared). Stacked with K-quant and fused-coset on the BitNet dimm2 path: K=8 plain 973.2 s → K=6 762.3 s → +fused 623.5 s → +phase-2 343.7 s = −64.7% vs the K=8 baseline, still answering "…Paris".
Why recv is the round-trip latency term, and it is synchronous — only pipelining sends past receives overlaps it. K-quant removes trips, fused-coset packs the array work, phase-2 attacks the receive itself; the three touch different terms, so they compose cleanly (fused-coset is opt-in, server default 0; the stack enables it explicitly).
Pointed to The current frontier number, −64.7% (973.2 → 343.7 s) — it supersedes the first campaign's 632 → 47.5 s / 13.3× and the never-materialized "~2×" as the headline. Made a production default 07-28 (a production-behavior change, user-gated).

X-master-clone — a clean −9.9%, then the discipline earned its keep closed negative methodology

Tried Write each activation plane's x once as a master row per request, then RowClone master→tuple in the MAJ3 bodies instead of re-writing all ~1,280 slots every round (MAJ3 destroys its operand rows each execution).
Result Implemented 07-27; a thin run read −9.9% and was written up as validated. It was not. That gate was max-tokens-1 ("1"=="1"), committed minutes after its own coherence probe launched. On the real production V2S path the tokens were garbage — and the first hypotheses ("intrinsic to the lever", "a streaming artifact") were both wrong: K=8 was garbage too, and stream-off in the exact config still babbled, so the axis was the model path. A purpose-built V2S oracle (same binary, shape, seed) found it: the RowClone'd master seeds x at charge-shared, not write-driven, levels (in-DRAM x′ ≠ x). Dual-track stays coherent-shaped but never clears the bar — the corruption is depth-independent (corr ≈0.94–0.97 flat across depths 8–80 rounds at production density, 0/2048 bit-exact), because masters refill every round so per-round seed errors never accumulate; single-track V2S (y = 2·pc(x′) − Σx, host-exact Σx) doubles the error uncancelled → token garbage. Oracle matrix: V2S XM=0 bit-exact 2048/2048, XM=1 corr 0.951.
Why A passing token — even a full-model one — is not a numerics proof, exactly as the layer-0 gate had already shown for M3. The adoption bar is per-op correlation (corr ≥ 0.98) at production depth, never a shallow shape or a token.
Pointed to Closed negative and hard-gated (&& !single on both tracks, V2S now inert); the −9.9% retracted. Verified oracle-to-full-model: the whole stack with the X-master flag set now returns "…Paris" at 351.0 s (the 343.7 s clean stack — yesterday's garbage arm green). The cleanest demonstration of the project's numerics-gate discipline — and it kills the "resident-constants → ~2×" story that once rode on this lever.

The through-line

The cost model, earned the hard way — and defended against three levers that looked like wins. Every "obvious" wall was attacked and came back neutral or worse — readback bytes (SEG_POP), drain wakes (ACCUM_XBP), instruction count (M3's first gate moved the wall only 4× despite cutting instructions 265×, and in the live server never moved it at all). The one quantity whose reduction reliably moved the wall was the host↔DRAM round-trip count, and specifically the receive latency — but streaming the send alone turned out to be wall-neutral (recv is synchronous); only phase-2, pipelining sends past receives, finally cut it, by 26.3% on silicon, and K-quant took a second axis, stacking to −64.7%. Program count never was the wall (K-batching, tried, +19.3%). Every neutral and negative verdict was load-bearing — and two of them (M3, X-master) were killed only because the adoption bar had moved from "answers Paris" to per-op correlation at production depth. And the deepest lesson wasn't about the wall at all: the two hardest bugs of the month were a structural determinism dressed as noise, and a years-latent fault dressed as a rare race — both invisible until a control run and a randomized testbench forced them into the light. The house rule that nothing is "noise" until an experiment proves randomness paid for itself again and again.
