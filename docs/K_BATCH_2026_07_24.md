# K-batching (PIM_INLINE_BITPLANES) — the dormant program-count lever

**Date:** 2026-07-24. **Origin:** the 3b request-path decomposition
(from the #31 wall run's srv-prof lines): V2 request wall ≈103 ms =
recv 62 ms (60%) + exec-send 20 + wcol 14 + other 7, with recv ≈
194 µs × **320 exec programs/request** at K=1 — and SEG_POP's
byte-halving wall-neutrality already proved bytes don't matter:
**program COUNT is the wall.** `PIM_INLINE_BITPLANES` (built May,
gated then by the 2K IMEM) has been runnable since the 8K bitstream
validated on 07-17 — production simply never turned it on.

## Gate (same-process twins — the post-inversion methodology)

- Instrument: server `PIM_K_ALTERNATE=1` (per-request effective K
  alternates 1/hi via `g_req_K`; counter increments once per V2/MM3D
  request) + `replay_ab.py --dup` on the captured production stream
  (`reqcap.b2`, 1100-record prefix: 35 LOAD, 720 MM3D, 345 V2).
- **First attempt (K=8) HUNG 11 h**: fused MM3D program = 8258 insts
  > 8192 IMEM; the platform oversize guard fired and predicted the
  deadlock verbatim; the truncated program left execute()'s
  completion poll spinning at 100% CPU. Two fixes: the server-side
  fit WARN is now a **CLAMP** (worst-case 416 insts/body × 4 banks →
  K=8 clamps to 4), and replay runs unbuffered (the hang was
  invisible for hours behind Python block-buffering).
- **K-gate v2 (K=1 vs K=4 twins): GATE ≡ CONTROL.**
  MM3D 104/720 differ (control 103/720 — the refresh-straddle rate;
  616 twins BIT-EXACT across K values), V2 345/345 at the rerun
  floor (elements 802,409 vs control 802,454), same first-diff
  request (#17), same value signatures. K=4 is as-correct-as-rerun.

## WALL RESULT: NEGATIVE — and the mechanism is the real finding

Stream K=4: **forward = 2,205.1 s** vs stream K=1 = 1,847.6 s
(**+19.3% — regression**). srv-prof decomposition:

  K=1: total=103ms  wcol=14 (120x)  exec=20ms (320x)  recv=62ms
  K=4: total=124ms  wcol=14 (120x)  exec=41ms  (80x)  recv=61.5ms

1. **recv is UNCHANGED at ÷4 program count ⇒ under PIM_STREAM, recv
   is SILICON-EXECUTION-bound, not wake-bound.** Rung-1 already hid
   the per-program round-trip; the 62 ms is the DDR-side compute +
   readout time itself. The "program count is the wall" inference
   (from SEG_POP's legacy-era byte-neutrality) was WRONG under
   streaming. K-batching attacks a solved problem.
2. **exec-send doubled (20→41 ms at 4× program size, ÷4 count)** —
   program finalization/serialization is superlinear in instruction
   count (branch preprocessing ~O(n²)); visible tax at scale, worth
   remembering for phase-2 where send cost sits on the critical path.

VERDICT: production stays K=1. Keep: the IMEM CLAMP (safety), the
PIM_K_ALTERNATE twin instrument, the 11-h-spin lesson. The corrected
wall map for the next levers:
  request wall 103 ms = 62 ms silicon (attack: M3 coset-deposit
  shrinks write+body work; Road-B/in-DRAM accumulation shrinks
  readout beats) + ~41 ms host-side send/build NOT fully overlapped
  (attack: phase-2 pipelining — send program N+1 while N's payload
  drains; potential ≈ −35% request wall if fully hidden).
