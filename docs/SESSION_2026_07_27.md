## 1. Phase-2 send-ahead — ENABLED + VALIDATED on silicon (−26.3%)

**What it is.** Under Rung-1 streaming the MM3D/V2 loop is still `execute` then a
*synchronous* `receiveData`; streaming the SEND cannot help while the RECV
blocks. Phase-2 pipelines the next program's send PAST the current recv
(`PIM_STREAM_PIPE`), attacking the recv term (~64% of the request wall)
directly.

**Result (full-model A/B, live build-26, no flash).**

| arm | wall | per-request recv | per-request total |
|---|---|---|---|
| `PIM_STREAM_PIPE=1` (phase-2 on) | **1863.1 s** | **57 ms** | 130 ms |
| `PIM_STREAM=1`, pipe off (control) | 2529.1 s | 112 ms | 176 ms |
| delta | **−26.3% wall** | **recv halved** | −26% |

- Token exact (`'The'`, full model), OFF and ON.
- **0 stalls / 0 decay / 0 errors over 11,500 requests.** The `~1/4k`
  lost-record stall that kept this lever default-OFF (see
  `docs/PHASE2_PIPE_2026_07_24.md`) does **not** reproduce — expected ~3
  occurrences if present. The RTL blocker is gone.

**Why the blocker cleared.** The "waiting on build-11" note in the roadmap was
STALE. build-11's loss-window fix never reached fabric (Synth 8-7071:
`fetch_restart` left unconnected in `softmc_core.v`, unread through builds
11/12/13). The true fix landed in **build-14** (magic `0x0D`, a 3-line wiring
fix connecting `fetch_restart`/`restart` through the QUAD wrapper); the running
**build-26** (`0x15`) is later still. So phase-2 was measured against fabric
that already carries the fix.

**Correction to the record — streaming does NOT "invert the regime."** The
earlier framing held that Rung-1 streaming makes bus-time (instruction count)
the wall, so the M3 265.8× instruction cut becomes the top post-streaming
lever. Silicon refutes the premise: with `PIM_STREAM` on vs off, recv is
**unchanged** (~64% of the wall) because the receive is synchronous — streaming
the send alone is **wall-neutral** (the −4.0% production A/B on 2026-07-23 was
phase-1 magnitude, not a regime change). The recv term only moves when the send
is pipelined PAST the recv — that is phase-2, and it is what delivers the
−26.3%. Instruction-count levers (M3, K-batching) do not become top levers
under streaming; the corrected wall map holds (recv is the trajectory).

**Status.** UNBLOCKED for production enable — flipping the `PIM_STREAM_PIPE`
default is a production-behavior change and is **USER-GATED**. Currently
default-off.

## 2. A working V2 numerics gate (output-vs-CPU-oracle on the real path)

The workspace had **no full-coverage output-numerics gate**: the old
`run_layer0_all_projections.py` oracle was deleted, `ab_fused_server.py` fails
silently (it drives the DISABLED `MAGIC_LOAD/MM3D` handle path — 0 program
executions, returns all-zero `y` masked by the LOAD-time verify), and
`l0_gate.sh` token-identity is insensitive (it passed at 87% wrong PIM masks,
because layer-0 puts only 7 of 210 BitLinears on PIM). Both halves of the gate
were built and validated this session.

**(a) `mm3d-verify` widened past round-0.** New env `PIM_VERIFY_ROUNDS`
(default `1` = old round-0 behaviour, byte-identical; raised = strided across
all rounds). Rebuilt + proven on silicon (Bonsai A/B: `ROUNDS=1` → 8192
segs/handle vs `ROUNDS=-1` → 16384 = all rounds; DECAY=0, token-exact). An OOB
on a partial final round (empty `exp_pc`) was caught in adversarial review and
guarded. Covers the RESIDENCY path; production is V2-dominant (pool exhausts
~handle 3) so it rarely fires there. The POST-MM3D verify block is a known
not-yet-widened gap.

**(b) V2 output-oracle — `/home/deni/Claude/numerics_gate/v2_oracle.py`.**
Drives the REAL `MAGIC_V2` production path (`process_request`, the same client
wire the model uses), builds a CPU reference from the SAME masks and bitplane
factors, and compares per element. It refuses to fail silently: asserts
response length (2048 int32), asserts `y ≠ 0`, and parses the server's own
`[srv-prof …] exec=…ms (Nx)` counter to assert `exec > 0` and
`exec_count ≥ n_rounds`. Carries a working negative control (`--inject-fault`:
the reference is computed from a mask differing by exactly one ternary weight,
so a *correct* server MUST mismatch).

- **`PIM_BACKEND=sim`: 8/8 bit-exact** (packing/protocol correct); the
  self-test negative control catches a 1-weight fault. Card-free — usable as
  the V2 numerics gate without touching silicon.

**KEY finding — the gate must be CORRELATION-based, not bit-exact.** Raw per-op
V2 silicon output is **NOT** bit-exact: the SAME op across fresh server
processes gave a bit-exact count that swung **28 / 459 / 463 / 283 of 512** —
intrinsic analog MAJ3 flake plus per-boot operating point (the cross-process
floor). A bit-exact verdict therefore over-fires and its rate is
process-dependent (the cross-process-compare trap). The oracle verdicts on
**correlation** instead: flake = signal + small noise → corr ≈ 1; wrong
weights / stale masks compute a DIFFERENT matvec → corr collapses. Measured
**corr = 0.997–0.9998, STABLE** across the very processes whose bit-exact count
swung 283→463. The threshold (corr ≥ 0.98) is **provisional** — calibrate it
against a real corruption run (a full-model stale-mask config) before trusting
the boundary. The oracle must run on production-shape (≤16-chunk) requests;
per-op divergence grows with round depth, not corruption (corr ~0.92 on an
80-chunk single-op is depth, not error).

This also reframes the historical "99.98% output-match": that was a
post-scale / aggregate / tolerance measure, NOT raw per-op popcount exactness —
which is why raw per-op looks far worse.

**Rule (recorded).** Gate mask/weight/pool changes on **numerics** (correlation
oracle), never on token identity. A full-model token run is an integration
check, not a numerics gate.

## 3. X-master-clone — activation-side residency + clone (−9.9%, default-off)

**What it is.** On the fused-coset path the 5 activation `wrRow`s (~1,280 PHY
slots each) rewrite THE SAME `x` plane every round — forced because MAJ3
charge-sharing destroys its operand rows each execution. X-master writes each
plane's `x` MASTER row once per request (8 planes × banks, outside the tuple),
then RowClones master→tuple positions (~40 slots vs ~1,280) per body. Both
primitives were already silicon-validated (safe-load 16/16 clone-into-tuple;
persistent-weight 2.6×/MAJ, 2026-07-17) — the activation side was simply never
wired.

**Implementation + verify.** Server path behind `PIM_XMASTER` (default 0) plus
a twin instrument `PIM_XMASTER_ALTERNATE`. Independent adversarial verify
confirmed **default-off byte-identical** (byte-diff vs a pre-change reference)
and caught a res-const deposit-screening gap for the `PIM_XMASTER` + `PIM_RC_V2`
pairing — FIXED (extra screen in `setup_x_masters`). Engages **8/8 masters on
all 4 banks**; numerically correct at production request-shape (d_in=512:
corr 0.998, within flake).

**Wall is request-shape-dependent.**

| shape | total | note |
|---|---|---|
| single-op d_in=2560 | 87.8 → **69.8 ms (−20.5%)** | exec −25%, wcol −15%; amortization works at scale |
| small op d_in=512 (16 chunks) | net-**NEGATIVE** | per-round master-fill overhead > savings when few bodies reuse each master |

Production splits projections into ≤16-chunk requests (the small regime), so
the single-op number does not transfer directly. The honest measure is the
full model:

**Full-model A/B (2026-07-27): X-master PAYS −9.9%.**

| arm | wall |
|---|---|
| `PIM_XMASTER=1` (on) | **1387.7 s** |
| off (control) | 1541.0 s |
| delta | **−9.9%** |

- Token-identical OFF == ON, **0 stalls / 0 decay**. A real, correct production
  throughput lever.
- **Requires fused-coset** (`PIM_FUSED_COSET=1`), which is server default 0.
  Stays **default-off** pending a user decision to enable, and its −9.9% only
  cashes in if fused-coset is adopted.
- ⚠ Both arms produced the token `'1'` (not `'The'`) — this is from
  `PIM_FUSED_COSET=1` (opt-in), NOT from X-master (OFF == ON) and NOT the
  production default. Production = fused OFF + phase-2 on = `'The'` (safe). The
  V2 correlation oracle says the fused compute is numerically correct
  (corr 0.998), so `'1'` is likely a valid completion — but it DIFFERS from the
  documented fused-coset `'Paris'`. **Open follow-up: verify whether
  fused-coset regressed to `'1'` (multi-token run) before adopting fused or
  X-master.**

## 4. Rung-2a on-fabric orchestrator probe — Verilator PASS 27/27

**What it de-risks.** Rung-2 moves the projection loop onto the card so the host
sends `x` and receives `y` — one round-trip per projection instead of
thousands, removing the recv term at the root (phase-2 / streaming only *trim*
it). Before any soft-core / microcode engineering, one question needed
isolating: **can the fabric run the loop and return exact integer partials with
no per-step host command?** No prior artifact connected command-issue →
DRAM-content → popcount → accumulate in one fabric-driven loop.

**The probe.** A closed-loop Verilator top (`rung2_probe_2026_07_27/`) wiring
the EXISTING `seq_engine` command generator → a DETERMINISTIC SiMRA DRAM model
(MAJ3 = bitwise majority, on purpose) → the EXISTING exact popcount + accumulate
datapath, driven by a small hard-coded sequencer that walks one projection's
chunk/bitplane loop. TB sends `x` once, reads the integer partials once,
byte-compares to a CPU oracle. Because the DRAM model is deterministic, a byte
mismatch means a control/datapath WIRING bug — never cell noise. Silicon MAJ3
exactness is already separately characterized (selection law, cross-die
byte-identical spread) and is deliberately NOT re-litigated here.

**Result.** **27/27 runs PASS, 0 FAIL — byte-exact** (fabric integer partials
== CPU oracle). Cases = 3 edge (all-zero → 0, all-ones → 8·512, `W₊`=ones →
pc(x)) + 3 chunk-counts {1, 8, 64} × 8 seeds. Feasibility established: the
fabric CAN drive a host-command-free projection loop and return exact integer
partials. This is a de-risking probe, not a soft core, ISA, allocator, or
refresh scheduler — those remain the Rung-2 build (design deep-dive in
`rung2_sequencer_design_2026_07_27.md`).
