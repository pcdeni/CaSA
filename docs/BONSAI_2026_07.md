# Bonsai-1.7B (PrismML) on the CaSA PIM path — first silicon results

*2026-07-20/21. Status: first-run, correctness-first record. Numbers in
this page are measured on the hardware described in `HARDWARE.md`; the
throughput figures are deliberately un-optimized (see §5).*

## 1. What this is

Until now everything in this repository ran one model: Microsoft's
BitNet b1.58-2B-4T. This page records the first **second model family**
through the same in-DRAM matmul path: **PrismML Bonsai-1.7B**, in both of
its released weight variants —

| Variant | Weights | Format |
|---|---|---|
| Bonsai (1-bit) | {−1, +1}, no zeros | w = s·t with one fp16 scale per **group of 128 consecutive inputs** ("g128") |
| Ternary Bonsai | {−1, 0, +1} | same g128 group-scale format |

Bonsai models are extreme quantizations of Qwen3 (here: Qwen3-1.7B — 28
layers, hidden 2048, GQA, 151k vocab), published by Prism ML, Inc. under
Apache-2.0, loadable as stock `Qwen3ForCausalLM` (no custom code). We run
the `-unpacked` checkpoints from Hugging Face (`prism-ml/Bonsai-1.7B-unpacked`,
`prism-ml/Ternary-Bonsai-1.7B-unpacked`). (Not to be confused with the
older, unrelated deepgrove/Bonsai 0.5B model.)

Why it matters for this repo:

- **Generality.** The pipeline was built around BitNet's ternary
  BitLinear. Bonsai has a different architecture family (Qwen3), a
  different scale structure, and in the 1-bit variant a weight alphabet
  with **no zeros at all**. All 196 projection matmuls (28 layers ×
  q/k/v/o/gate/up/down) ran in DRAM with the **server binary unchanged**.
- **Group-wise scales are the industry direction.** Every llama.cpp-style
  quantization format carries per-group scales; BitNet's single
  per-tensor scale is the exception. Supporting g128 makes the client
  format-general rather than BitNet-specific.
- **1-bit as a degenerate dual-track.** The client's ternary convention
  (positive mask + negative mask) absorbs pure ±1 weights as a
  dual-track with an **empty zero-set** (`neg_mask = ~pos_mask`, masks
  ~50% dense instead of ~30%) — zero changes to client or server. The
  negative track is then mathematically redundant
  (`y = 2·y_pos − Σᵢxᵢ`), which makes a future single-track mode a free
  2× on pool rows and MAJ3 work for 1-bit models.

## 2. What was changed (and proven unchanged)

Client only (`python/pim_linear.py`, `python/run_bitnet_pim.py` — shipped
in this repo): an optional `weight_spec` path that loads external
`codes` (int8) + `group_scales` (f32 [out, in/128]) + sparse residuals,
builds **per-group request bodies** (one 4-chunk window per 128-input
scale group), votes on integer partials *before* applying scales, and
applies a host-side sparse-residual correction (~1e-5 of weights sit a
few fp16 ulps off their group level in PrismML's unpacked export;
correcting them costs nothing and makes the weight path exact).

With the feature off (`--model bitnet`, the default), the client was
regression-proven **byte-identical**: same outputs and the same wire
stream — every request body, length prefix, and ordering, 255 requests,
130,087,716 bytes, matching sha256 — as the pre-change client.

Weight-path exactness (both variants, layer 0, all 7 projections, sim
backend): PIM outputs **bitwise equal** to a numpy mirror of
`codes·x` + group rescale + residuals, across the V2, LOAD, and
dual-server dispatch modes; integer per-group partials 100.0000% exact.
The only lossy element in the whole path is the client's per-token int8
activation quantization (§5).

### 2.1 The verification identities (measured, not assumed)

Four identities were checked before any silicon time
([`BONSAI_PREP_2026_07_20.md`](BONSAI_PREP_2026_07_20.md) §6,
`docs/data/bonsai/verify_report.json`):

- **A — Reconstruction.** `W = codes · repeat(group_scales) + residuals`
  is **bit-exact against the shipped fp16 tensors for all 392 projection
  tensors** (both variants). Without the sparse residuals, max deviation
  9.77e-4 — PrismML's unpacked export leaves ~1e-5 of weights a few
  fp16 ulps off their group level; the extraction carries them as exact
  sparse deltas.
- **B — Dual-track popcount identity.** The pos/neg-mask popcount
  arithmetic over 8 activation bitplanes (factors 1…64, −128) equals
  int64 `codes @ x` **exactly** — the extraction is consumable by the
  existing machinery unmodified.
- **B1 — 1-bit single-track identity.** With zero-free ±1 weights,
  `neg_mask = ~pos_mask`, hence `y = 2·y_postrack − Σᵢxᵢ` (verified
  exact). The neg track is redundant for 1-bit models — a server
  single-track flag would halve pool rows and MAJ3 work; deliberately
  not implemented yet (correctness first, on unchanged machinery).
- **C — Group rescale.** `y = Σ_g s[r,g]·(codes_g·x_g)` with residual
  correction equals the f64 reference at **exactly 0.0**.
- **D — Activation-quant bound.** BitNet-style per-token int8
  quantization vs the model's own fp matmul: max deviation 0.05–0.16
  per output on unit-normal activations — the one real approximation,
  quantified before committing to it (§5).

Two design decisions worth recording: sub-handles are clamped so **no
handle ever straddles a 128-input scale-group boundary** (each group =
exactly four 32-input chunks), and voting runs on **integer per-group
partials before scales are applied** (median semantics on ints are
well-defined; k/v's in-row replication shares rows and therefore
scales, keeping vote-then-scale valid).

## 3. Silicon verdict (2026-07-20, single DIMM, vote off)

Full model, all 196 projections in DRAM, greedy decoding, prompt
"What is the capital of France?", compared token-by-token against an
fp32 CPU golden of the same checkpoint:

| run | variant | prompt mode | generated (verbatim) | vs golden |
|---|---|---|---|---|
| 1 | ternary | raw | ` The capital of France is Paris. Paris` | **8/8 token-exact** |
| 2 | 1-bit | raw | ` What is the capital of France? What` | **8/8 token-exact** (the golden echoes identically — see below) |
| 3 | 1-bit | chat | `The capital of France is Paris.` (+ eos) | **8/8 token-exact**, incl. the eos stop |

Zero FPGA incidents across all three runs.

The run-2 echo is the model's own behavior, reproduced faithfully: in
raw (no chat template) mode the 1-bit variant degenerates to base-style
repetition — the fp32 golden does exactly the same — while the ternary
variant answers even in raw mode, and the 1-bit variant answers
correctly in chat mode (run 3). The pipeline is transparent enough that
the *capability difference between two quantizations of the same base
model* is directly visible on DRAM silicon.

### 3.1 The two quantizations, side by side (fp32 golden, 16-token greedy)

| Variant / mode | Golden CPU continuation |
|---|---|
| ternary / raw | ` The capital of France is Paris. Paris is a city located in the north of` |
| ternary / chat | `The capital of France is Paris. It is a major city located in the north` |
| 1-bit / raw | ` What is the capital of France? What is the capital of France? What is` |
| 1-bit / chat | `The capital of France is Paris.<|im_end|>` … |

The 1-bit variant loses enough capability that out-of-distribution raw
continuation collapses into repetition, while the chat template restores
instruction-following (PrismML's own 27B benchmarks show the same
ordering: ternary retains ~94.6% of FP16 quality, 1-bit ~89.5%). The
silicon runs reproduce each cell's behavior token-exactly
(`docs/data/bonsai/golden_{ternary,1bit}.json` hold the exact ids).

## 4. Throughput (first-run, un-optimized)

- ~**100 s/generated-token** (both variants) in the 7-in/8-out raw
  shape on **one DIMM**, vote off; **57–58 s per token-position**
  across all three runs (the shape-independent number; run 3's
  31-token prefill amortizes to the same per-position rate).
- Requests per token-position: **~5,826–5,831 measured** ≈ **6.2× the
  per-token request count of BitNet-2B at vote parity**. This is the
  price of group-granular rescale: one request per 128-input scale
  group instead of 1–4 per output slice. Total in-DRAM MAJ3 work per
  token is roughly unchanged — the growth is round-trip overhead, and
  the logs confirm it: >99% of wall time is pipe reads; server-side
  compute is 3–9 s per run.

  | requests | per layer-token | full model per token |
  |---|---|---|
  | Bonsai, vote on | 560 theoretical / ~500 measured (sim) | ~15,680 |
  | Bonsai, vote off | 208 | 5,824 (measured 5,843 incl. LOAD probes) |
  | BitNet-2B, vote on (same harness) | ~85 | ~2,550 |

- Determinism cross-checks came free: the sparse-residual term count is
  exactly per-position-deterministic (silicon run 1 = 2× the sim
  7-position count; run 3 = exactly 38 × the per-position count), and
  the 1-bit/ternary runs issue **identical request counts** (81,627) —
  the protocol is weight-value-independent.
- The measured ladder so far (same shape, same tokens, all golden-exact):

  | config | s/generated-token | vs baseline |
  |---|---|---|
  | single-DIMM, vote off (07-20) | 100.0 | 1× |
  | + dual-DIMM split (07-21) | 51.2 | 1.95× |
  | + fused coset (07-21) | **33.7** | **2.97×** |

  Details: the addendum below and §7.

## 5. Honest caveats

- **Activation quantization is a real (bounded) deviation.** The
  unpacked Bonsai reference computes fp16-activation matmuls; our path
  quantizes activations to int8 per token (as BitNet does natively, and
  as PrismML's own deployed llama.cpp kernels do in spirit). Measured
  end-to-end in simulation: step-0 logit deviation ≤0.47 on logits of
  magnitude ~12–15, argmax agreement, top-16 overlap 16/16 (ternary) /
  15/16 (1-bit). Validation standard is therefore **token agreement**,
  not logit bit-exactness. Long generations may diverge from the fp16
  golden; the 8-token runs above did not.
- **Vote was off** (correctness-first protocol; the golden-exact result
  made the vote-on contingency unnecessary).
- **Nothing was tuned.** The optimization arms that exist for BitNet
  were deliberately not exercised in the first runs: the fused coset
  activation update, the 1-bit single-track mode, and a server-side
  group-rescale extension (returning per-4-chunk partial vectors, or a
  per-handle scale table) that would remove the 6.2× request
  amplification itself. These are staged, not speculative — each has a
  designed mechanism and a measured BitNet analog.
- **Fused coset: cleared on silicon after the simulator rejected it** —
  a small story about trusting the right instrument; see §7.
- **Model fit**: Bonsai-1.7B needs ~11,648 pool rows/bank for full
  residency vs ~180 available per die today, so it runs in the same
  LOAD-then-stream regime as BitNet-2B production (~3% resident). Same
  machinery, no new pool planning.

## 6. Reproduction

```bash
# weights (HF): prism-ml/Bonsai-1.7B-unpacked, prism-ml/Ternary-Bonsai-1.7B-unpacked
# extraction: codes/group_scales/residuals per projection (npz), then:
BITSTREAM_IMEM=8192 PIM_NO_CHAT_TEMPLATE=1 PIM_VOTE_FULL=0 \
python3 run_bitnet_pim.py --model bonsai_ternary --dimms 2 --bank 0,1,2,3 \
    --prompt "What is the capital of France?" --max-tokens 8
# --model bonsai_1bit for the 1-bit variant; drop PIM_NO_CHAT_TEMPLATE for chat mode.
```

The golden references are fp32 CPU greedy runs of the same checkpoints
(stock transformers); the client-environment CPU forward reproduces the
golden logits bit-exactly, so every silicon deviation is attributable to
the PIM path.

## 7. Sim vs silicon: the fused-coset A/B (2026-07-21)

The fused coset activation update (the lattice-addressing lever that
replaces per-activation row writes with one co-activation deposit —
see [`LATTICE_ADDRESSING_2026_07.md`](LATTICE_ADDRESSING_2026_07.md))
was BitNet-production-validated but never exercised under group mode.
The clearing sequence is worth recording in full:

1. **Sim rejected it.** With `PIM_FUSED_COSET=1`, the simulator produced
   grossly wrong integer partials for every 4-chunk LOAD-resident
   sub-handle (`exact=0/2048`) and for the n_copies=2 replicated k/v
   slices — two distinct failure signatures
   (`docs/data/bonsai/sim_fused_ternary_{load,v2}.log`).
2. **Silicon passed it, 35/35.** The identical configurations on the
   real DIMM — fused × 4-chunk LOAD, fused × replication, fused ×
   copy-vote — are **100.0000% integer-exact, zero exceptions**
   (`docs/data/bonsai/sil_q_fused.log`, `sil_k_fused_vote.log`). The
   physical co-activation deposits into all rows; the simulator's fused
   emulation does not model that for these two shapes. The failure was
   the instrument's, not the mechanism's.
3. **Full-model clearing run** (pool-scale bugs are invisible at
   layer 0): ternary, raw, 8 tokens, `--dimms 0,2`, fused on —
   **8/8 golden-exact, 269.2 s = 33.7 s/generated-token**. Against the
   same-morning non-fused dual-DIMM run: **1.52× from fused alone**;
   against the 07-20 single-DIMM baseline: **2.97× stacked**, all three
   configurations producing the identical golden-exact text.

One honest prediction correction: we expected fused to be
throughput-neutral for Bonsai ("the wall is >99% pipe reads"). Wrong —
the client's "pipe-read" time *is* the server's per-request service
time, which is DRAM-program-execution-bound; fused shortens every MAJ3
body, and ~1.7 ms × 81,689 requests accounts for the 140 s saved. The
production recommendation for Bonsai is now `PIM_FUSED_COSET=1`.

## Addendum (2026-07-21): dual-DIMM measurement

Same shape as run 1 (ternary, raw prompt, 7-in/8-out, vote off), with
`--dimms 0,2`: each projection's scale groups round-robin across two
concurrently driven DIMMs, integer partials merged on the host.

- Output: ` The capital of France is Paris. Paris` — the same 8/8
  golden-exact continuation as the single-DIMM run.
- **8 tokens in 409.9 s = 51.2 s/generated-token**, vs 799.7 s /
  100.0 s/token single-DIMM — **1.95×, 98% of the ideal-halving bound**
  (29.3 s per token-position). The group-granular protocol balances
  *by construction*: the two servers received byte-identical request
  volumes (2,618.4 MB, 40,845/40,844 calls) and their pipe reads ran
  concurrently (~398 s each, replacing ~788 s serial).
- Zero FPGA incidents; same LOAD→V2 streaming regime on both dies.

The round-trip wall parallelizes across DIMMs almost perfectly for
group-mode traffic — the 6.2× request amplification (§4) divides by the
DIMM count until the server-side rescale extension removes it outright.

## Addendum (2026-07-21 PM): the 1-bit single-track protocol — 18.7 s/tok

For the 1-bit variant the zero set is empty, so the negative track is
the exact complement of the positive track — computing it in DRAM is
pure duplication. `PIM_1BIT_SINGLE=1` activates a new wire protocol
(`MAGIC_V2S`): requests carry the pos masks only, the server enumerates
half the (chunk, sign) units, and the client reconstructs

    y = 2·y_pos − Σ_b fac_b · popcount(x_b)

per response (the correction is host-known; ternary/zero-carrying
slices auto-fall-back to dual-track; grouped-response and resident-
weight paths stay dual). Validated bitwise-exact in sim across four
configurations — with engagement proven by cost, not just flags: the
sim server's wall halved (30.9 → 16.0 s).

Silicon A/B (raw mode, vote off, fused dual-DIMM — the §Addendum ladder
convention, 8 generated tokens):

| arm | wall | s/tok | output | requests | bytes on the wire |
|---|---|---|---|---|---|
| dual-track | 270.2 s | 33.8 | token-exact golden echo | 40,845 | 2618 MB |
| **single-track** | **149.3 s** | **18.7** | **token-identical** | 40,845 | **1316 MB** |

**1.81× per token — the per-request path itself collapsed 1.90×**
(259.2 → 136.4 s pipe time) at an identical request count: requests do
not halve, per-request DRAM work does, which is exactly the designed
shape. The measured ladder is now single-DIMM 100 → dual 51.2 → +fused
33.7 → **+single-track 18.7 s/tok (5.36× stacked)** — and the 1-bit
variant now *beats* ternary on the wall: the first quantization-level
property to become a throughput lever on this pipeline.

Chat-mode caveat (measured, discriminated): on **dual-DIMM + fused**,
the chat run produced `…is **Paris**` — one token off the golden
`…is Paris.` The discriminator (same config on the clean DIMM only) is
**golden-exact**, so the flip is DIMM-0's fused-marginal
content-conditional floor — the same mechanism the group-response study
exposed — not the single-track protocol. Guidance: single-track always;
dual+fused where throughput rules (raw output token-identical);
single-clean-DIMM or dual-without-fused where chat token-exactness is
required. (Whether dual+fused chat flips even without single-track is
untested — the floor likely predates the protocol.)
