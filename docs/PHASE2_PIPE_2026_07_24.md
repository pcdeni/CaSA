# Phase-2 send-ahead pipeline (PIM_STREAM_PIPE) — 2026-07-24

**Target:** the corrected wall map's ~41 ms/request of host build+send
not overlapped with silicon time (request wall 103 ms = 62 ms silicon
+ ~41 ms host). Design: every exec flows through pend_recv +
consume_one; pipe OFF = consume immediately (byte-identical platform
call sequence); pipe ON = receives defer so later rounds' build+send
hides under earlier rounds' silicon. Send order — and the DDR-side
timeline, hence the 2026-05-04 write-then-use locality constraint —
unchanged by construction.

## The unbounded-deferral hang (and its geometry)

First implementation deferred ALL receives to a request-end drain →
DETERMINISTIC hang at the first pipe-ON twin. Captured live (no
ptrace needed — /proc/<pid>/task/*/wchan):
- drain thread: S, wchan=xdma_engine_read_cyclic (c2h starved — the
  FPGA stopped producing);
- main thread: R, wchan=0 (receiveData spinning on the empty
  api_recv_buf at the final drain).
Diagnosis: the build-9 ping-pong was only ever validated with the
host ≤1 program ahead (phase-1's recv pacing guaranteed it);
unbounded h2c send-ahead outruns execution and loses programs
(idle-bank clobber class). NOT a host-buffer limit (API_BUF_SIZE
2 MB > the 670 KB full-deferral footprint). Follow-up filed: box-TB
verification of frontend tready backpressure at >1-ahead; RTL
hardening if absent.

Fix: **PIM_PIPE_DEPTH (default 1)** — bounded send-ahead inside the
validated envelope. Depth 1 already hides the host per-program
build+send (~128 µs) under the ~194 µs silicon time.

Full-model run (stream + pipe depth-1): ran CLEAN for 3,850+ requests
with **total ≈ 71–75 ms, recv ≈ 25–30 ms** per V2 request (baseline
103 / 62 ms) — the projected phase-2 gain, measured. Then STALLED

Read: a ~1/4,000-request LOST-RECORD event under exec-overlap —
depth-1 exec sends overlap COMPUTE-program execution, silicon

wcol payload-0 sends ever ran ahead; the build-9 ladder overlapped
READ programs only). A lost program = a silently missing record — no
poison (nothing malformed arrives), the pending recv waits forever.
The twin gates (345 pipe-on twins) were an order of magnitude too
short to see it; the correctness result stands (gate ≡ control).

VERDICT: PIM_STREAM_PIPE stays default-OFF. The −30% is real and

## RC-V2 (consts-into-V2) twin gate: ELEVATED — and correctly read

wall delta. Wall run (stream, no pipe, PIM_RC_V2=1) IN FLIGHT vs the

## BUILD-11: root causes FIXED, regression ALL_PASS, Vivado LAUNCHED

The trace decode found TWO RTL defects + one TB-model bug:
1. **Stale-pc loss window (THE production stall):** fetch re-loops
   pc=0..END between END and fin; any hold/state-exit parks pc at an
   arbitrary phase and the NEXT program resumes from it — losing its
   first word(s), or a short program entirely. LATENT IN LEGACY TOO
   (scenario H: legacy + long fins loses words) — masked historically
   by fixed-fin TBs and phase luck. FIX: `fetch_restart` strobe —
   pc=0 forced at every program start (streamed swap, legacy INIT_MEM
   handoff, maintenance entry).
2. **fin/tlast same-cycle race:** fin landing the cycle a program's
   tlast stages it took the slow-producer IDLE path, stranding the
   staged bank. FIX: count the same-cycle staging in the fin branch.
3. TB fin model rebuilt: per-program fin queue + once-per-executed-
   program arming (the old global latch mis-timed fins under eager
   sends and produced false failures).

REGRESSION: A-H + F(5 seeds × 4,000 programs) **ALL_PASS**.
Build-11 (magic 0xDBC0DE0A) synthesizing on the box (build11.log);
staging checklist clean (md5 match, magic grep). After USER JTAG
flash: ladder + stream suite + twin gates re-run, then the pipe and
consts walls — the measured −29% and −31% unlock together.

## BUILD-11 SILICON: loss window CURED, but a new regression — and the
## proper fix (build-12, park-at-END)

Flash + ladder verdict (magic 0A): **A–E13 ALL PASS** (the restart fix
cured the stale-pc loss window on silicon) but **E14 REPRODUCED
in reverse** — streamed BRANCH-LOOP writes corrupt on build-11
(8/8 rows, ~95% bytes; legacy arm model-exact; E14 passed on
build-10). Mechanism class: `fetch_restart` un-parks the previous
program's re-loop from its branch/hold park, making stale fetch
state execute-visible. Production fused bodies contain branch-loop
wrRows ⇒ **PIM_STREAM default reverted to OFF for build-11**.

The deeper read: every hazard in this family (stale pc, stale
branch pairing, post-END junk) is a symptom of ONE disease — the
post-END re-loop. **Build-12 removes the disease: fetch PARKS at END
(new WAIT_RESTART_S state) until the frontend's restart strobe**, +
br_outstanding fence (stale resolves dropped), + the maintenance-site
restart pulse removed (maintenance bypasses fetch; un-parking there
was the prime E14 suspect). TB gained branch coverage (scenario I —
branches were tied off before; the gap that let build-11 through).
Note honestly: the exact E14 pairing was never reproduced in sim
(the TB lacks the decode/execute side); build-12 wins by removing
the ingredients, and the silicon E14 rerun is the real gate.
